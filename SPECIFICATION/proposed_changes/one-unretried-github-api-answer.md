## Proposal: Every forge read the incident-ci job makes retries an unreadable answer, prints what it got, and an unreadable pull-request body fails the selection by name

### Target specification files

- SPECIFICATION/contracts.md
- SPECIFICATION/scenarios.md

### Summary

Add three paragraphs to `## Expedited incident execution`, before the trusted-label paragraph, and one scenario. Every forge read the incident-ci job makes retries an attempt that carries a 5xx status, got no status, or answered with a body that is not JSON: at most five attempts, waits of 2, 4, 8 and 16 seconds, 30 seconds per attempt. Every other answer fails at once. Each failed attempt prints the read, attempt, HTTP status, kind and the first 256 escaped bytes of the answer. When the pull-request body read fails every attempt, the selection step fails naming it and never treats the unreadable body as armed, as carrying a block or as lacking one. The kinds and the HTTP-marker rule are the fleet `gh` read-failure classification's; only `not_json` is added, and `rate_limited` is deliberately not retried. The read is defined once for workflow steps as a new composite Action, `forge-read`, which puts `livespec-forge-read` on the job's path; consumers pin it by release tag. The released entrance applies the same rule through the package's budgeted `gh` boundary. §"Composite Actions wire contract" gains the Action's bullet.

### Motivation

Work item livespec-dev-tooling-levu6j (plan expedited-incident-response-flag, epic livespec-dev-tooling-bqnzcm) is held at its spec-change tier: its filing judgement (spec v204, linked topic `one-unretried-github-api-answer`) found that the ratified text never says the incident-ci job's forge reads retry, print what they got, live in one shared definition, or fail by name without selecting incident work. The only retry rule, the fleet `gh` read-failure classification, governs the fleet conformance surface, not this job.

The defect, measured. `.github/workflows/ci.yml` reads the forge in the `incident-ci` job with bare `gh api` under `bash -e -o pipefail`: the latest-release read (`gh api "repos/${GITHUB_REPOSITORY}/releases/latest" --jq .tag_name`, ci.yml:931), which runs on EVERY event, and the selection step's pull-request body read (`gh api "repos/${GITHUB_REPOSITORY}/pulls/${PR_NUMBER}" --jq '.body // ""'`, ci.yml:966), which runs on every pull request. On livespec-dev-tooling#4339, an ordinary unarmed pull request, run 43243495155 job 131269893794 failed at the body read with `invalid character 'S' looking for beginning of value`: GitHub answered with a body that was not JSON, the step printed nothing else (no status, no bytes), and because `incident-ci` is in `ci-green`'s `needs` the required check went red. The released entrance makes a third read in-process (`livespec_dev_tooling/incident_ci_event.py:31`, one `gh_read` of `repos/{repository}/pulls/{number}` with no retry); it runs on every pull request whose body carries a block, including an unexpedited factory-repayment follow-up that retains one, so the same transient answer can redden that pull request too, which is why the rule covers it.

Why now. Under the maintainer's adopt-all ruling (epic livespec-dev-tooling-bqnzcm, 2026-11-12T14:56Z) every consumer in livespec core's committed `.livespec-fleet-manifest.jsonc` will carry an `incident-ci` job, so a read copied inline into this ci.yml would spread to 21 more repositories. The ruling is recorded here, not in the spec.

Shared-home decision: a composite Action, `forge-read`, not a released `livespec_dev_tooling` module. (1) The latest-release read is what LOCATES the released package, so a released module cannot make it: the job installs the release only after that read (ci.yml:927-946), and in this repository the only package present before it is the candidate tree. (2) Consumers already pin this library's composite Actions from their `ci.yml`; the bump-pin rewrite already rewrites those `uses:` refs (`github_workflow_uses_ref`, `.github/actions/bump-pin-rewrite/action.yml`), and the fleet audit's template reader already reads `.github/actions/...@ref` pins as serving evidence (`livespec_dev_tooling/_incident_fleet_template_reader.py`), so a consumer's served version of the read is pinned, bumped and audited by machinery that exists. A module would reach a consumer only through its Python dependency pin, and a consumer whose incident-ci job reads the forge before any `uv sync` could not use it. (3) The Action puts a COMMAND on the job's path rather than performing the read as its own step. The reads therefore stay inside the steps that use them: the selection step keeps its shell event test and its single `block=present` write, which `tests/consumer/test_ci_incident_scratch_push.py` pins, and no step of this gating job gains an event-conditioned `if:`, which the job's design (the event/PR distinction is made in the shell, ci.yml:870-871) and the wiring test's `event_conditioned` rule exclude. (4) The one deliberate second home is the released entrance's in-process read: the entrance runs only released code (`-I`, ci.yml:987-988), and in this repository `./.github/actions/forge-read` is candidate-tree code, so the entrance applies the same stated rule through `livespec_dev_tooling/budgeted_gh.py`, the package's one `gh` read boundary, whose client is already built with `max_attempts=1` precisely because "retry policy belongs to the caller". The rule (what is retried, bound, waits, time limit, printed line) is stated once, here.

Bound and backoff chosen: five attempts, waits of 2, 4, 8 and 16 seconds (30 seconds in all), and a 30-second limit per attempt, so a read that fails every attempt ends within three minutes, well inside the job's 90-minute timeout, while a GitHub blip of up to half a minute is ridden out. Relation to the fleet `gh` read-failure classification (contracts.md §"Cross-repo coordination automation surface", the paragraph headed "A `gh` failure's status needs its HTTP marker"): the incident read reuses its HTTP-marker rule and its kinds, adds only `not_json` (that classification classifies refused reads, and a 2xx answer that is not JSON is not one), and decides retries by status and body rather than by kind. It deliberately does not retry `rate_limited`, which the fleet seam retries, because a 30-second wait cannot outlast a rate-limit window.

In-flight alignment (align with every item). livespec-dev-tooling#4333 (v205, the enablement record; its twin #4328 carries the same bytes) appends paragraphs at the END of `## Expedited incident execution` and its scenarios after the fleet-audit command scenario. livespec-dev-tooling#4311 inserts four paragraphs immediately AFTER the trusted-label paragraph and its scenario after `an expedited PR defers coverage and spec work while master runs normally`. The draft under topic `the-fleet-audit-can-read` (branch spec/the-fleet-audit-can-read, not yet a pull request) inserts after the scratch-installation paragraph and after the paragraph that begins "The fleet audit MUST expand", and adds scenarios after the scratch-drill and installed-fleet-capability scenarios. This proposal inserts only BEFORE the trusted-label paragraph (after the repair-output paragraph) and its scenario only BEFORE `an expedited PR defers coverage and spec work while master runs normally`, gaps no draft above touches, so all of them still apply in any merge order. livespec-dev-tooling#4336 (topic `a-gate-job-retries-a`, §"Delegated pre-push gate") retries the gate Job's anonymous git fetches and treats an anonymous 401 or 403 as transient; that is compatible: those are anonymous git-transport reads whose 401 the forge also answers for transient egress refusals, while the incident-ci reads are authenticated REST reads whose 4xx answers carry JSON and are final.

Out of scope, named as follow-ups. `.github/workflows/incident-label-ci.yml` reads the forge with the same bare `gh api` pattern; it is left alone here, as the work item directs, and it can adopt `livespec-forge-read` in a later item. `ci-green`'s own job-list read (`gh api --paginate .../actions/runs/${GITHUB_RUN_ID}/jobs`, ci.yml:1152) has the same exposure inside the required aggregate and is also not covered. The checkout and the `uv pip install git+https://...@<tag>` fetch are git-transport reads, not REST reads, and are governed elsewhere (livespec-dev-tooling#4336, #4337).

### Proposed Changes

### contracts.md §"Expedited incident execution"

Insert the following three paragraphs immediately after the paragraph that begins "Repair output MUST contain a legal adjacent code/test comment" and immediately before the paragraph that begins "A trusted PR-specific label plus structured receipt MUST project mode only into the exact repair PR/head before initial CI." This gap is chosen so that no in-flight draft inserts into it (see the in-flight alignment in the Motivation):

> Every forge read the `incident-ci` job makes MUST retry an answer it cannot read, so that one unreadable answer never decides the job. The rule covers every read the job makes through the GitHub REST API: each read a workflow step of the job makes (today the latest-release read that locates the release the job installs, and the pull-request body read that selects incident work) and the released incident CI entrance's own read of the pull request. The released incident CI entrance (the entrance) is `python -m livespec_dev_tooling.incident_ci_process`, which the job installs from this library's latest release and runs only on a pull request whose body carries a `livespec-incident-ci` block. An attempt MUST be retried when it carries an HTTP 5xx status, when it got no HTTP status at all, including an attempt stopped at its time limit, or when its answer body does not parse as JSON whatever its status. An attempt whose status is 2xx and whose body parses as JSON is the read's answer. Any other attempt, such as an HTTP 401, 403, 404 or 429 answer whose body parses as JSON, MUST fail the read at once without a retry. A read MUST make at most five attempts, MUST wait 2, 4, 8 and 16 seconds before the second, third, fourth and fifth attempt, and MUST stop each attempt after a time limit of no more than 30 seconds, so a read whose every attempt fails ends within three minutes. An attempt's status MUST be taken only from an HTTP status the answer presents as one, as the fleet `gh` read-failure classification (§"Cross-repo coordination automation surface") requires, never from a bare digit run. Each failed attempt MUST be named by that classification's kind for its status (`server_error`, `rate_limited`, `forbidden`, `not_found`, or `transport` for an attempt with no HTTP status or with any other status), or by `not_json` for a 2xx answer whose body does not parse as JSON. The kinds are that classification's; the retry decision is this paragraph's. The two differ in one place: the fleet seam retries `rate_limited`, and this read MUST NOT, because its whole wait of 30 seconds is shorter than a rate-limit window, so it fails at once naming `rate_limited`.

> Each failed attempt MUST print one line naming the read, the attempt number out of five, the HTTP status the attempt carried (`none` when it carried none), its kind, and the first 256 bytes of the answer body, or of `gh`'s standard error when the attempt got no body. Those bytes MUST be printed on that one line with every line break, control byte, non-ASCII byte and backslash written as an escape, so that no answer can open a line of its own or a workflow command. When every attempt of the latest-release read fails, its step MUST fail with an error naming that read and its last status. When every attempt of the pull-request body read fails, the selection step MUST fail with an error naming the pull-request body read and its last status, and MUST NOT write its `block` output, so the entrance does not run and the job writes no `omitted` value. A body that could not be read MUST NOT be treated as carrying a `livespec-incident-ci` block, as armed, or as lacking a block: the step MUST NOT select incident work from it and MUST NOT report that it selected nothing. When every attempt of the entrance's read of the pull request fails, the entrance MUST refuse with a cause naming that read, and MUST NOT observe an event from it.

> For workflow steps the retrying read MUST be defined once, as this library's composite Action `forge-read` (§"Composite Actions wire contract"). The Action puts one command on the job's path, `livespec-forge-read <read-name> <endpoint>`, which makes the read the two preceding paragraphs define and writes the JSON answer to its standard output. Every forge read a workflow step of an `incident-ci` job makes MUST go through that command, in this repository and in every consumer that carries an `incident-ci` job, and an `incident-ci` job MUST NOT carry its own retry loop or a bare `gh api` read. This repository's job MUST use the Action from its own tree (`./.github/actions/forge-read`), as it uses its other Actions; a consumer MUST reference it at a release tag of this library, in the `uses:` pin form this library's bump-pin rewrite already rewrites. The Action's files are part of the published surface that carries the `incident-ci` job, so the fleet audit MUST count them among the files of every surface row whose files include `.github/workflows/ci.yml`. The entrance's own read MUST apply the same rule through this package's own GitHub read boundary, `livespec_dev_tooling.budgeted_gh`, never through the Action: the entrance runs only released code, and in this repository the Action is candidate-tree code.

### contracts.md §"Composite Actions wire contract"

Replace "The library MUST ship at minimum four composite Actions:" with "The library MUST ship at minimum five composite Actions:", and append the following bullet after the `publish-flake-retries` bullet, as the list's last entry:

> - **`forge-read`**. Inputs: none. Outputs: none. Permissions: none of its own; each read authenticates with the calling job's `GH_TOKEN` and needs only the permission its endpoint needs. Performs: one step that adds the Action's own directory to the job's `GITHUB_PATH`, so that every later step of the job can run `livespec-forge-read <read-name> <endpoint>`, the retrying forge read §"Expedited incident execution" defines. The command MUST need nothing beyond bash, the `gh` CLI and `python3`, so that it runs before the job installs any Python package, and it MUST NOT print the token it reads with.

### scenarios.md

Insert the following scenario immediately after the closing fence of `## Scenario: incident commit provenance remains verifiable on normal master` and immediately before `## Scenario: an expedited PR defers coverage and spec work while master runs normally`, its body in a ```gherkin fence as its neighbours are:

> ## Scenario: an incident-ci forge read retries an unreadable answer and an unreadable pull-request body fails the selection by name
>
> ```gherkin
> Given an ordinary pull request whose body carries no `livespec-incident-ci` block
> And GitHub answers the incident-ci job's pull-request body read with a body that is not JSON on the first attempt, with HTTP 502 on the second and with the pull request's JSON on the third
> When the incident-ci job runs on that pull request
> Then each of the two failed attempts MUST print one escaped line naming the pull-request body read, its attempt number, its HTTP status and kind, and the first bytes of its answer
> And the selection step MUST read the third attempt's answer, select nothing and pass
> And when GitHub instead answers all five attempts with an HTTP 5xx status, the selection step MUST fail naming the pull-request body read and its last status, MUST NOT write its block output and MUST NOT report that it selected nothing
> And the released incident CI entrance MUST NOT run, and the job MUST NOT write an omitted value
> And an HTTP 404 answer whose body is JSON MUST fail the read at its first attempt without a retry.
> ```
