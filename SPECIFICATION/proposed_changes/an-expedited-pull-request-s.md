## Proposal: An expedited pull-request run and its omitted members are recorded on the incident work item by the independent controller and read without the forge

### Target specification files

- SPECIFICATION/contracts.md
- SPECIFICATION/scenarios.md

### Summary

Defines an expedited pull-request CI run as a run of the incident CI job on a pull-request head the independently hosted released controller has armed for an incident item; a run on an unarmed head, including one whose aggregate refused for want of a current arm, gets no record. Every such run becomes an item-linked record on the incident work item, bound to the repository, item, attempt, generation and retained arm, the pull request, base and head, the run id and run attempt. A published record, written from a PASSED aggregate, carries the controller build, the passed members, the deferred members with reasons, the omitted members (the deferred members whose reason is the coverage or spec policy, exactly the list the `omitted` output carries) and the aggregate digest; `failed` and `missing` are empty by construction for a PASSED aggregate, so the published content is the passed, deferred and omitted members. An unpublished record carries exactly the run id, the run attempt, the incident CI job's conclusion and the code of any refusal the controller answered to that run's publication. The writer is the controller, through the ledger port its verified installation already holds, in the same marked-record family and through the same canonical ledger the original-run evidence uses, so reading the item's records returns every expedited pull-request run of every attempt without a forge read. The incident CI publisher - the step that today uploads the outcome records as a forge artifact - publishes the PASSED aggregate to the controller under the protected CI invocation identity the controller already verifies for a CI job attachment; the runner never holds a tenant credential. Completeness does not depend on the publication: from the workflow-job completion delivery it already receives, the controller records the unpublished record, and every refusal it answers, `identity-not-provisioned` included, is written onto that item record, not only into the forge step summary. livespec-dev-tooling-bqnzcm.4 owns provisioning `ci_identity_policy` through the committed `incident_observer` Ansible role as the first step of its implementation, and its host proof is captured on that provisioned production installation. One scenario is added after `## Scenario: an expedited PR defers coverage and spec work while master runs normally`.

### Motivation

Work item livespec-dev-tooling-bqnzcm.4 (plan expedited-incident-response-flag, epic livespec-dev-tooling-bqnzcm), split from bqnzcm.2 by the coordinator's cut of 2026-11-12 10:41Z, carrier of gap G3 of completeness review bqnzcm-completeness-review-20261112T100929Z. Its spec-change tier record (2026-11-12 11:16Z, spec v203, generalization target `## Expedited incident execution`) says the ratified text requires expedited PR jobs to expose executed, failed and deferred results in the stable protected aggregate and requires retention of original failed master CI, but never says the CI publisher records an expedited PR run's id and omitted members as item-linked records on the incident work item, or that those records can be read without the forge. Measured on the closed incident livespec-dev-tooling-t26bbr (A14 READS comment, 2026-11-11T21:29:21Z): `context t26bbr --json` reaches all four attempts, the PRs, merges, the revert, the master runs, the focused evidence, the deferred spec debt and the original-run evidence digest, but NOT the expedited PR runs 43028964670 and 43042866644 or their omitted-by-incident-policy members, which live only on the forge and in the plan epic's comments.

Where things are today (read 2026-11-12 at master a40114a6). `.github/workflows/ci.yml` job `incident-ci`: its step `Publish the incident CI outcome records` is `actions/upload-artifact@v4` of `tmp/incident-ci` as the `incident-ci-outcomes` artifact with `retention-days: 7`; the aggregate itself is printed to the log and the step summary, and the `omitted` job output is read out of the passed aggregate's `deferred` rows with reason `incident-policy:coverage` or `incident-policy:spec`. The job holds `contents: read` and `pull-requests: read` only, and the ratified text says the flag grants no credential, so the runner cannot write the tenant. The only incident surface that holds the tenant credential is the independently hosted released controller (`reader.env` beside its protected `controller.json`), and it already records item-linked evidence this way: `_incident_original_run_canonical.py` writes the original-run evidence on the incident item as a marked comment (`livespec-incident-original-run-evidence-v1` followed by JSON) keyed by item id, attempt id, generation, run id and run attempt, idempotent by digest, through the controller's ledger port, and `recorded_digests` reads it back from the item's comments with no forge read (docs/incident-original-run-evidence.md). The controller also already (a) retains per-job CI attachments in the `ci_job_attachments` subtree of its protected record, bound to the retained arm's incident item, attempt, operation, generation, owner and phase plus PR, base, head, run id, run attempt, job, check and suite ids, authenticated by the forge-issued OIDC identity token at `POST /ci/attach` (docs/incident-ci-identity.md), and (b) receives GitHub `workflow_job` completion events at its HMAC-verified `POST /callback` (docs/incident-observer.md). `aggregate_ci_results` in `incident_ci_policy.py` publishes `passed`, `failed`, `missing` and `deferred` members for the current head and scope.

Candidates weighed. (1) The job writes the tenant: rejected, it has no credential and the flag grants none. (2) The controller derives the omitted members from the run's job steps through its read-only forge token: rejected, `check-metadata-batch` reports omission through a shell function inside one step that the jobs API cannot see, and the ratified posture is that canonical operations are not emulated from local state. (3) The controller downloads the `incident-ci-outcomes` artifact: rejected, it carries outcome rows rather than the published aggregate, it needs an `actions: read` zip download, and it expires after seven days, so a record owed past that is lost. (4) The job publishes the passed aggregate to the controller under the protected CI invocation identity, and the controller records the item-linked record through its ledger port: chosen. Every key the record needs is already in the attachment binding, the controller is already the component every incident vantage trusts, and the ledger write reuses the writer that records original-run evidence. One precondition is recorded rather than hidden: plan research 004-incident-drill-arming-procedure.md (section 5) measured that the production installation's manifest has no `ci_identity_policy`, so `/ci/identity` and `/ci/attach` are not provisioned today, and docs/incident-ci-identity.md names provisioning an approved immutable reusable workflow and issuer keys as operator obligations. The proposal therefore makes completeness independent of the publication (the controller records every incident CI job completion on an armed head from the delivery it already receives) and makes a not-provisioned controller a named refusal that does not fail the job, so the plan's first Definition of Done bullet (an operator can deliver an expedited fix without a precondition blocking the repair) stays true through the rollout, following CLAUDE.md section 'Ordering - confirm the reader before you write'. The sibling proposal `the-incident-execution-resolver-does` (livespec-dev-tooling#4305) appends at the end of the same section and adds its scenarios after the fleet-audit scenario; this proposal inserts after the trusted-label paragraph and adds its scenario after the expedited-PR scenario, so the two touch different lines and are compatible (alignment: align).

### Proposed Changes

In `SPECIFICATION/contracts.md`, section `## Expedited incident execution`, insert the following four paragraphs immediately after the paragraph that begins "A trusted PR-specific label plus structured receipt MUST project mode only into the exact repair PR/head before initial CI." and before the paragraph that begins "Add an incident-specific subsection to `Master-health reconciler`".

```text
An expedited pull-request CI run is a run of the incident CI job on a pull-request head that the independently hosted released controller has armed for an incident item, whatever that job's conclusion. A run of that job on a head the controller has not armed, including one whose aggregate refused because no arm was current, is not an expedited pull-request CI run: it MUST receive no record, and nothing in the following three paragraphs applies to it.

Every expedited pull-request CI run MUST be recorded on the incident work item as an item-linked record that the incident item's records answer without reading the forge. A record is either published or unpublished, and each kind MUST bind the repository, the incident item, the attempt, the generation and the retained arm whose head the run ran on, the pull request with its base and head, the run id and the run attempt. A published record is written only from an aggregate that PASSED, at most one per run attempt, and MUST additionally carry the released controller build that produced the aggregate, the aggregate's passed members, its deferred members with each deferral's reason, the omitted members (the deferred members whose reason is the coverage or spec policy, exactly the list the `omitted` output carries) and the aggregate's digest. A PASSED aggregate has empty `failed` and `missing` members by construction, because its success requires at least one passed member and no failed or missing member, so the published record's content is the passed, deferred and omitted members and the record MUST NOT carry a failed or missing list. An unpublished record MUST carry exactly the run id, the run attempt, the incident CI job's conclusion and, when the controller answered a publication for that run attempt with a refusal, that refusal's code; it carries no members. Reading the incident item's records MUST return every expedited pull-request run of every attempt of that item, with its omitted members when published and its conclusion and refusal code when not, in the same marked-record family and through the same canonical ledger the original-run evidence uses, so that an operator inspecting the item by its id alone sees them beside the attempts, merges, reverts and master runs. The records are append-only and idempotent by binding and digest: a repeated publication of the same aggregate MUST answer the retained record and write nothing, and a different aggregate for the same run attempt MUST be recorded as a conflict record naming both digests, never as a replacement.

The writer is the independently hosted released controller, through the ledger port its verified installation holds. No runner job, factory worker or candidate tree MAY write the record: the incident CI job holds the read-scoped Actions token only and the flag grants no credential. The incident CI publisher, the step of the incident CI job that publishes the outcome records, MUST publish the released aggregate to the controller only after that aggregate has PASSED, authenticated by the protected CI invocation identity the controller already verifies for a CI job attachment (the forge-issued identity token for the job and the exact retained arm query), and MUST publish nothing on a refused aggregate, an unexpedited pull request or a run that carries no incident block. The job MAY request the forge-issued identity token for this purpose; that permission is not a workflow write scope and grants no credential beyond the job's own identity. The controller MUST verify the publication exactly as it verifies an attachment, outside the repository effect lock, against the identical unrevoked retained arm, MUST retain the aggregate digest and omitted list in that job's attachment slot in its protected record, and only then MUST record the published record through the ledger port. A publication whose pull request, head or arm differs from the retained arm MUST be refused as stale and MUST record no published record. The record authorizes no current effects, no CI admission, no merge and no factory proof, and every publication reply MUST carry the same four false authority fields as an attachment reply.

Completeness MUST NOT depend on the publication succeeding. The controller MUST retain, in that run attempt's attachment slot, the code of every refusal it answers to a publication, and it MUST write that code onto the item: from the trusted completion delivery of individual workflow jobs it already receives, the controller MUST, on the completion of the incident CI job of an expedited pull-request CI run for which it retained no publication, record the unpublished record for that run attempt carrying the job's conclusion and the retained refusal code, if any; a later publication for the same run attempt records its own published record beside it and replaces nothing. A retained refusal for which no record exists on the item by the controller's next due sweep pass MUST be recorded then, with the conclusion `unknown`, so that a lost delivery cannot leave a refused run unrecorded. A refusal that reaches only the forge step summary is not a record. A controller whose installation manifest carries no CI identity policy MUST answer a publication with the named refusal `identity-not-provisioned`, distinct from an unavailable verification, and MUST write that code onto the item as above; the publisher MUST also write it to the aggregate's step summary and MUST let the job conclude on the aggregate alone, so that an operator can still deliver an expedited repair before the installation provisions identity. On any other refusal, and when the controller cannot be reached, the publisher MUST fail the incident CI job naming the cause, because an expedited run whose omissions are not recorded is unaccounted work; this is the fail-closed posture the aggregate's own admission rechecks already take. The publisher MUST NOT retry a publication the controller refused as stale under a different head. livespec-dev-tooling-bqnzcm.4 owns provisioning the CI identity policy, and the order is normative: the first step of that item's implementation MUST provision `ci_identity_policy` on the production installation through the committed `incident_observer` Ansible role, applied by the normal committed route and never by a hand write on the host; that item's host proof MUST then be captured on that provisioned production installation; and until the provisioning is applied, every expedited pull-request CI run MUST be recorded on the item as an unpublished record carrying `identity-not-provisioned`, so that the gap is visible on the item rather than silent.
```
