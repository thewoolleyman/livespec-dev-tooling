## Proposal: The incident observer role renders one production installation per repository its committed inventory declares

### Target specification files

- SPECIFICATION/contracts.md
- SPECIFICATION/scenarios.md

### Summary

Add two paragraphs after the scratch-installation paragraph of `## Expedited incident execution`. The first requires a committed inventory of production observer installations, one rendered per declared repository, each with its own configuration naming that repository and its required CI jobs, its own manifest, state directory, reference clone of that repository, tenant, port and units. livespec-dev-tooling's installation stays byte-identical when it is the only one declared, and converging or removing one installation never touches another. The second states the webhook ingress: every production installation publishes its routes on the role's one funnel port. livespec-dev-tooling keeps `/callback` and `/ordinary-action`, and every other installation publishes them under `/<name>/`, proxied to its own listener only, judged against the union of declared paths. Scratch installations still publish nothing. Add one scenario.

### Motivation

Work item livespec-dev-tooling-lqp2qx (pending-approval) is held at its spec-change tier (verdict partial, spec v204): the ratified text covers ONE scratch installation beside ONE production installation, and never says the role renders a production installation per repository. Plan expedited-incident-response-flag (epic livespec-dev-tooling-bqnzcm) needs one for each of the three adopting repositories besides livespec-dev-tooling (livespec, livespec-orchestrator-beads-fabro and livespec-overseer, under the ruling recorded below) before their controller and recovery rows can classify as implemented.

What the code does today:

- `ansible/roles/incident_observer/defaults/main.yml:21` hard-wires `incident_observer_repository: thewoolleyman/livespec-dev-tooling`, and `:41-53` is livespec-dev-tooling's own `ci.yml` leaf-job list, held to that file by `tests/livespec_dev_tooling/test_incident_observer_job_universe.py`. The role renders exactly one production installation (`templates/controller.json.j2:4` names one repository).
- The role can already render a SECOND installation with its own configuration, manifest, state directory, reference clone, port and units, but only as a scratch instance (`vars/scratch.yml:24-38`; `defaults/main.yml:163-172`).
- The reference clone is cloned from `incident_observer_release_repo` (`tasks/converge.yml:285-286`), which is livespec-dev-tooling, and the canonical reader's tenant pointer and credential are single values (`defaults/main.yml:122-124`, the projected `BEADS_DOLT_PASSWORD` and the livespec-dev-tooling tenant's `project_id`). Another repository's installation needs a clone of THAT repository and THAT repository's tenant (each family tenant has its own `dolt.server-user` and database in its `.beads/config.yaml`), so the proposal states both.
- Each listener already refuses a callback, and every authenticated request, that names any repository but its own (`livespec_dev_tooling/incident_observer_service.py:112-114` and `:202`).

Open implementation question, recorded for the item rather than decided here: the role writes one tenant credential, the projected bare `BEADS_DOLT_PASSWORD`, and one tenant `project_id` (`defaults/main.yml:122-124`). Each family tenant has its own database user, so one role run that converges installations for several tenants needs a credential for each. The clause requires each installation's reader to read its own tenant. It does not prescribe how the credential wrapper projects several tenants' credentials. livespec-dev-tooling-lqp2qx, or a per-repository child, owns that question.

Ingress decision (lqp2qx's Context asks for it). The funnel is production's alone and path-scoped: `defaults/main.yml:133-151` publishes exactly `/callback` and `/ordinary-action` on funnel port 10000, and `tasks/converge.yml:674-691` skips every funnel task for a scratch instance. Tailscale Funnel admits only ports 443, 8443 and 10000, and 8443 is already served on the dev host (`defaults/main.yml:137-138`), so a funnel port per installation leaves only 443 for the three further installations the ruling below needs, and none for any later adopter. The role already publishes exact paths with `tailscale funnel --set-path=<path> http://127.0.0.1:<port><path>` (`tasks/converge.yml:781-799`), so a path prefix per repository on the same port is the shape it already uses. livespec-dev-tooling keeps its unprefixed paths, so its installation and the webhook URL GitHub already delivers to stay byte-identical (the `byte-identical` rule of the scratch paragraph and lqp2qx's second Definition of Done bullet). The role's undeclared-path refusal (`tasks/converge.yml:843`, "Refuse a funnel port that publishes a path beyond the declared list") would refuse on a sibling installation's paths, so the proposal makes it judge against the union. Scratch installations keep publishing nothing and stay host-local, as the ratified scratch paragraph requires. The tailnet front of production's listener is a host_vars mapping (`ansible/inventory/host_vars/vps.yml:211-213`, 8765 to 127.0.0.1:8765); the proposal requires each installation's tailnet routes to reach only its own listener, and leaves the mapping's form to the implementation.

## Proposal: The fleet audit reads each consumer's controller and recovery authorization from the installation that serves it

### Target specification files

- SPECIFICATION/contracts.md
- SPECIFICATION/scenarios.md

### Summary

Add a paragraph before "The fleet audit MUST be runnable". The audit reads each consumer's independent-controller serving version from the production installation the committed observer inventory declares for that repository, resolved only from that inventory or a test-held equal copy. The consumer's recovery-authorization reading uses that same installation's controller reading. A consumer no installation serves reads unverified, no reading comes from a scratch installation, and livespec-dev-tooling's readings are unchanged. Add one scenario.

### Motivation

Work item livespec-dev-tooling-iaysvp (pending-approval) is held at its spec-change tier (verdict partial, spec v204, linked topic `the-fleet-audit-can-read`): the clause makes the readers read "the running independent controller" and counts an unavailable read as unverified, but never says each consumer is read against its OWN installation, that the recovery reading reuses that installation's controller reading, or that livespec-dev-tooling's readings stay unchanged.

What the code does today:

- `livespec_dev_tooling/incident_fleet_controller_reader.py:31-33` pins `OBSERVED_REPOSITORY = "thewoolleyman/livespec-dev-tooling"`; `:34-41` names one unit (`livespec-incident-observer.service`) and one `--config /etc/livespec-incident/controller.json`; `:105-108` returns None for every other repository before any read. `tests/livespec_dev_tooling/test_incident_fleet_controller_reader.py:103-118` pins that constant to the role default and asserts another repository reads None with nothing asked.

Measured 2026-11-12 with `just incident-fleet-audit` on vps (master `2a4314a5b`): all three read `-` for both `independent-controller` and `recovery-authorization`, and each is named in a "lacks serving-version evidence for recovery-authorization, independent-controller" finding.

It does not loosen what counts as a readable build. It closes the hard-wiring by naming where the mapping comes from: the committed inventory the role renders from, so the reader and the installed units cannot drift. The unverified result for an unserved consumer is the behaviour the ratified clause already requires for an unavailable read, stated for this case. Under the ruling recorded in finding 1, the 18 deliberately-normal consumers are all unserved; finding 3 is what lets their deliberately-normal rows classify without these readings, so this paragraph does not have to treat them specially. No spec-reading test pins this section's text. Two tests pin today's shape and change with the implementation, not with this text. `test_incident_fleet_controller_reader.py:106` pins `OBSERVED_REPOSITORY` to the role default line, and `tests/livespec_dev_tooling/test_incident_fleet_serving.py:907` pins `PRODUCTION_READERS["independent-controller"] is read_controller_serving`. The scratch exclusion repeats the ratified scratch paragraph's "the fleet audit MUST NOT read it as the running independent controller" for the per-consumer case.

## Proposal: A deliberately-normal claim classifies from the decision it cites, and an instruction-only adopter's guidance rows can be claimed

### Target specification files

- SPECIFICATION/contracts.md
- SPECIFICATION/scenarios.md

### Summary

Add two paragraphs before "The fleet audit MUST be runnable". The first says a `deliberately-normal` claim's evidence is the decision it cites (who made it, when, where it is recorded), so the audit classifies its row without a release build or a serving read of the row's capability, while still printing any serving version it did read. A consumer with any `deliberately-normal` row is never ready, and a consumer whose rows are all `deliberately-normal` or `not-applicable` is not named in a "lacks serving-version evidence" finding. The second states the audit's existing treatment of an instruction-only adopter: its 35 runtime rows read `not-applicable` with no claim and `unclassified` with one, its two guidance rows classify from a committed claim, and it is never ready. Every check over the committed claims must accept what these paragraphs let the audit classify, including claims for an instruction-only adopter. Add one scenario, exercising the deliberately-normal path the maintainer's ruling uses.

### Motivation

Work item livespec-dev-tooling-kddu2b (pending-approval) is held at its spec-change tier (verdict unstated, spec v204): the ratified text says the audit expands every member and adopter into a consumer, but says nothing about how an instruction-only adopter's rows classify. The instruction-only rule it does state (non-functional-requirements.md §"Fleet manifest adopter profiles") belongs to the fleet-conformance sweep, not the incident fleet audit.

Under the maintainer's 2026-11-12T15:21:34Z ruling (quoted verbatim in finding 1), 18 manifest consumers are deliberately-normal, each claim citing that ruling: 11 that the audit treats as applicable consumers, and the 7 instruction-only adopters. Their rows have to classify `deliberately-normal` from those claims before the audit can complete.

What the code does today for an instruction-only adopter:

- The audit already treats it this way. `livespec_dev_tooling/incident_fleet_audit.py:62` names the two guidance surfaces; `:101` makes every other row of an instruction-only adopter inapplicable (read `not-applicable` with no claim at `:102-110`, and `unclassified` when a claim names it, through `_incident_fleet_row_gap.py:89-90`); and `incident_fleet_audit.py:150` keeps an instruction-only adopter off the ready list. Both guidance surfaces map to the `driver-hooks` capability (`_incident_fleet_capabilities.py`).
- The committed-claims test refuses every claim for one. `tests/livespec_dev_tooling/test_incident_fleet_committed_claims.py:75` with `:84` refuses every claim whose repository is not in `_applicable_consumers`, which drops instruction-only adopters (`livespec_dev_tooling/_incident_fleet_command.py:77-82`). So no instruction-only adopter's guidance row can be claimed in the committed file, deliberately-normal or otherwise.
- The audit also excuses an `implemented` claim on an instruction-only adopter's guidance row from the incident item, factory proof and scope digest (`_incident_fleet_row_gap.py:44`). That allowance is kept and stated, so the spec does not trail the code, but no claim under this ruling uses it, and the scenario exercises the deliberately-normal path instead.

What the code does today for a deliberately-normal claim, the gap behind both groups. The committed-claims test already accepts a deliberately-normal claim for the 11 applicable consumers: they pass `not-an-applicable-consumer`, a reason is required, and no incident record is, as long as the claim names a release build in its capability's serving form (`test_incident_fleet_committed_claims.py:45-55`). Once a deliberately-normal claim needs no release build, the test's `missing-field` and `release-build-not-serving-form` checks must not refuse its absence. The audit does not accept these claims. `row_gap` runs the serving check after the claim check for every disposition (`_incident_fleet_row_gap.py:91-93`), so a deliberately-normal row classifies only when its claim's release build equals a serving version the audit read and re-read for that row's capability. Measured 2026-11-12 with `just incident-fleet-audit` on vps (master `2a4314a5b`), these reads are unavailable:

- all 11 applicable deliberately-normal consumers read `-` for `independent-controller` and `recovery-authorization`, which together serve 8 of each consumer's rows (5 and 3, `_incident_fleet_capabilities.py:44-57`). Finding 1 builds installations only for adopters, so under this ruling these reads stay unavailable for good;
- openbrain, resume and homelab also read `-` for `gate-readers` and `templates`, and dolt-server and hetzner-xubuntu-info read `-` for `templates`;
- 5 of the 7 instruction-only adopters (fabro-hosts, gmktec-xubuntu-info, hp-xubuntu-info, otel-collector, poweredge-xubuntu-info) read `-` for `driver-hooks`, so even once the test admits them, their deliberately-normal guidance claims could not classify.

In addition, `_incident_fleet_command.py:174-182` names every applicable consumer that lacks any capability reading in a "lacks serving-version evidence" finding, and the command exits non-zero while any finding stands (`exit_code` at `:226-228`, through `FleetAudit.complete`). The same run named all 11 that way, so they would keep the audit from completing for good.

The proposal therefore changes what the audit accepts for a deliberately-normal claim. kddu2b's Context says "do not change what the audit accepts", so its Definition of Done has to widen to cover this, or a sibling item has to own the audit change; the plan owner decides which. The change is safe because a consumer with any deliberately-normal row is never listed ready (`incident_fleet_audit.py:143-157`), so no enablement ever rests on that row's serving version. Requiring the read would make a ruled-normal consumer's rows depend on installations the ruling decided not to build. The claim still binds the committed manifest identity and names its owner, source path and proof reference, and its reason must name the decision. A release build only means something when it is compared with a serving read, so the claim no longer needs one. An implemented claim keeps every serving check it has today. The existing scenario "the incident fleet audit command refuses enablement for a consumer without verified serving evidence" still holds for a consumer whose controller row is not claimed deliberately-normal, and the new scenario says so.

The two ratified requirements this qualifies are stated, not edited. "serving-version evidence" in the paragraph that begins "The fleet audit MUST expand core's committed manifest", and the requirement in "The fleet audit MUST be runnable" that the findings name each consumer lacking serving evidence, are each qualified by a sentence in the new paragraph that names them. livespec-dev-tooling#4326 edits sentences inside the "runnable" paragraph and v205 appends after it, so editing that paragraph here would collide with both.

The checks keep refusing a claim on an instruction-only adopter's runtime row, which they refuse today through `not-an-applicable-consumer`. Once that check admits instruction-only adopters, the refusal needs its own check, because the audit leaves such a row unclassified.
