## Proposal: The incident observer role renders one production installation per repository its committed inventory declares

### Target specification files

- SPECIFICATION/contracts.md
- SPECIFICATION/scenarios.md

### Summary

Add two paragraphs after the scratch-installation paragraph of `## Expedited incident execution`. The first requires a committed inventory of production observer installations, one rendered per declared repository, each with its own configuration naming that repository and its required CI jobs, its own manifest, state directory, reference clone of that repository, tenant, port and units. livespec-dev-tooling's installation stays byte-identical when it is the only one declared, and converging or removing one installation never touches another. The second states the webhook ingress: every production installation publishes its routes on the role's one funnel port. livespec-dev-tooling keeps `/callback` and `/ordinary-action`, and every other installation publishes them under `/<name>/`, proxied to its own listener only, judged against the union of declared paths. Scratch installations still publish nothing. Add one scenario.

### Motivation

Work item livespec-dev-tooling-lqp2qx (pending-approval) is held at its spec-change tier (verdict partial, spec v204): the ratified text covers ONE scratch installation beside ONE production installation, and never says the role renders a production installation per repository. Plan expedited-incident-response-flag (epic livespec-dev-tooling-bqnzcm) needs one for every code consumer before their controller and recovery rows can classify.

What the code does today:

- `ansible/roles/incident_observer/defaults/main.yml:21` hard-wires `incident_observer_repository: thewoolleyman/livespec-dev-tooling`, and `:41-53` is livespec-dev-tooling's own `ci.yml` leaf-job list, held to that file by `tests/livespec_dev_tooling/test_incident_observer_job_universe.py`. The role renders exactly one production installation (`templates/controller.json.j2:4` names one repository).
- The role can already render a SECOND installation with its own configuration, manifest, state directory, reference clone, port and units, but only as a scratch instance (`vars/scratch.yml:24-38`; `defaults/main.yml:163-172`).
- The reference clone is cloned from `incident_observer_release_repo` (`tasks/converge.yml:285-286`), which is livespec-dev-tooling, and the canonical reader's tenant pointer and credential are single values (`defaults/main.yml:122-124`, the projected `BEADS_DOLT_PASSWORD` and the livespec-dev-tooling tenant's `project_id`). Another repository's installation needs a clone of THAT repository and THAT repository's tenant (each family tenant has its own `dolt.server-user` and database in its `.beads/config.yaml`), so the proposal states both.
- Each listener already refuses a callback, and every authenticated request, that names any repository but its own (`livespec_dev_tooling/incident_observer_service.py:112-114` and `:202`).

Open implementation question, recorded for the item rather than decided here: the role writes one tenant credential, the projected bare `BEADS_DOLT_PASSWORD`, and one tenant `project_id` (`defaults/main.yml:122-124`). Each family tenant has its own database user, so one role run that converges installations for several tenants needs a credential for each. The clause requires each installation's reader to read its own tenant. It does not prescribe how the credential wrapper projects several tenants' credentials. livespec-dev-tooling-lqp2qx, or a per-repository child, owns that question.

Ingress decision (lqp2qx's Context asks for it). The funnel is production's alone and path-scoped: `defaults/main.yml:133-151` publishes exactly `/callback` and `/ordinary-action` on funnel port 10000, and `tasks/converge.yml:674-691` skips every funnel task for a scratch instance. Tailscale Funnel admits only ports 443, 8443 and 10000, and 8443 is already served on the dev host (`defaults/main.yml:137-138`), so a funnel port per installation cannot serve 13 code consumers. The role already publishes exact paths with `tailscale funnel --set-path=<path> http://127.0.0.1:<port><path>` (`tasks/converge.yml:781-799`), so a path prefix per repository on the same port is the shape it already uses. livespec-dev-tooling keeps its unprefixed paths, so its installation and the webhook URL GitHub already delivers to stay byte-identical (the `byte-identical` rule of the scratch paragraph and lqp2qx's second Definition of Done bullet). The role's undeclared-path refusal (`tasks/converge.yml:843`, "Refuse a funnel port that publishes a path beyond the declared list") would refuse on a sibling installation's paths, so the proposal makes it judge against the union. Scratch installations keep publishing nothing and stay host-local, as the ratified scratch paragraph requires. The tailnet front of production's listener is a host_vars mapping (`ansible/inventory/host_vars/vps.yml:211-213`, 8765 to 127.0.0.1:8765); the proposal requires each installation's tailnet routes to reach only its own listener, and leaves the mapping's form to the implementation.

## Proposal: The fleet audit reads each consumer's controller and recovery authorization from the installation that serves it

### Target specification files

- SPECIFICATION/contracts.md
- SPECIFICATION/scenarios.md

### Summary

Add a paragraph before "The fleet audit MUST be runnable". The audit reads each consumer's independent-controller serving version from the production installation the committed observer inventory declares for that repository, resolved only from that inventory or a test-held equal copy. The consumer's recovery-authorization reading uses that same installation's controller reading. A consumer no installation serves reads unverified, no reading comes from a scratch installation, and livespec-dev-tooling's readings are unchanged. Add one scenario.

### Motivation

Work item livespec-dev-tooling-iaysvp (pending-approval) is held at its spec-change tier (verdict partial, spec v204, linked topic `the-fleet-audit-can-read`): the clause makes the readers read "the running independent controller" and counts an unavailable read as unverified, but never says each consumer is read against its OWN installation, that the recovery reading reuses that installation's controller reading, or that livespec-dev-tooling's readings stay unchanged.

What the code does today:

- `livespec_dev_tooling/incident_fleet_controller_reader.py:31-33` pins `OBSERVED_REPOSITORY = "thewoolleyman/livespec-dev-tooling"`; `:34-41` names one unit (`livespec-incident-observer.service`) and one `--config /etc/livespec-incident/controller.json`; `:105-108` returns None for every other repository before any read. `tests/livespec_dev_tooling/test_incident_fleet_controller_reader.py:103-118` pins that constant to the role default and asserts another repository reads None with nothing asked.
- `livespec_dev_tooling/incident_fleet_serving.py:86-91` takes the recovery reading through a second `read_controller_serving` call, and `livespec_dev_tooling/_incident_fleet_recovery_reader.py:129-141` fails closed when that controller reading is None (`:133-134`).
- So even after a second repository gets its own installation (finding 1), the audit cannot see it, and none of the other 21 consumers' controller and recovery rows can classify.

The proposal keeps what the code does for livespec-dev-tooling, including the reader's refusal of any process whose command does not name the expected configuration (`incident_fleet_controller_reader.py:111-117`). It does not loosen what counts as a readable build. It closes the hard-wiring by naming where the mapping comes from: the committed inventory the role renders from, so the reader and the installed units cannot drift. The unverified result for an unserved consumer is the behaviour the ratified clause already requires for an unavailable read, stated for this case. No spec-reading test pins this section's text. Two tests pin today's shape and change with the implementation, not with this text. `test_incident_fleet_controller_reader.py:106` pins `OBSERVED_REPOSITORY` to the role default line, and `tests/livespec_dev_tooling/test_incident_fleet_serving.py:907` pins `PRODUCTION_READERS["independent-controller"] is read_controller_serving`. The scratch exclusion repeats the ratified scratch paragraph's "the fleet audit MUST NOT read it as the running independent controller" for the per-consumer case.

## Proposal: An instruction-only adopter classifies its two guidance rows from an implemented claim without an incident record

### Target specification files

- SPECIFICATION/contracts.md
- SPECIFICATION/scenarios.md

### Summary

Add a paragraph that states the audit's existing treatment of an instruction-only adopter: its 35 runtime rows read not-applicable with no claim and unclassified with one. Its two guidance rows classify from a committed claim that still needs its fields, the committed identity and the driver-hooks serving reading, but an implemented claim needs no incident item, factory proof or scope digest. It never appears on the ready list. Every check over the committed claims must agree with that. Add one scenario.

### Motivation

The claim must still name its source path, proof reference, owner and release build (`_incident_fleet_row_gap.py:40-41`) and still pass the serving check (`:52-69`), and both guidance surfaces map to the `driver-hooks` capability (`_incident_fleet_capabilities.py`, `Agent tool and stop guards` and `Operator factory routing`).
- The committed-claims test refuses what the audit accepts. `tests/livespec_dev_tooling/test_incident_fleet_committed_claims.py:66-72` requires the incident record of every implemented claim, and `:75` with `:84` refuses every claim whose repository is not in `_applicable_consumers`, which drops instruction-only adopters (`livespec_dev_tooling/_incident_fleet_command.py:77-82`). So no instruction-only adopter's guidance row can ever be claimed in the committed file.

Under the maintainer's 2026-11-12T14:56Z adopt-all ruling (quoted verbatim in finding 1), the 8 instruction-only host and infrastructure adopters adopt through exactly these two rows, so this gap blocks them all. The proposal states the audit's existing behaviour as the contract and requires the checks over the committed claims to agree with it. It does not change what the audit accepts. The checks keep refusing a claim on an instruction-only adopter's runtime row, which they refuse today through `not-an-applicable-consumer`. Once that check admits instruction-only adopters, the refusal needs its own check, because the audit leaves such a row unclassified.
