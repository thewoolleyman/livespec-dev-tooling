# gitops-fleet-capacity-monitoring — charter

Opened 2026-10-13 at the maintainer's direction, by the hp storage session (livespec-dev-tooling-smrzsj, closed).

## What this plan is

A **long-lived standing session** for the GitOps-managed fleet hosts (hp-xubuntu, poweredge-xubuntu, gmktec-xubuntu, vps). The maintainer uses it to ask ad-hoc questions about the fleet and to handle capacity and host incidents. Each concrete piece of work it takes on is a child work item. Questions answered in passing need none.

**Expiry.** This plan retires when the factory hosts move onto the Kubernetes infrastructure and these bespoke GitOps machines are retired, as the maintainer stated on 2026-10-13. Its Definition of Done is therefore deliberately narrow: the one capacity decision in flight at creation. Standing work beyond that is admitted as child work items and recorded in scope events.

## Where the fleet's capacity knobs live (this repo)

- hp's Fabro fleet cap: `ansible/inventory/host_vars/hp-xubuntu.yml`, `fabro_server_instances` → fleet instance `max_concurrent_runs: 10`. It has been live since 2026-10-13T07:11:52Z.
- Applying a cap change takes a Fabro server restart, which ends in-flight runs. The path is an inventory edit, then `just ansible-apply ansible/fabro-hosts.yml --limit hp-xubuntu`, with the other roles skipped and `-e fabro_server_manage_settings=true -e fabro_server_restart_allowed=true -e fabro_server_interrupt_runs_allowed=true`. The maintainer has ruled: **no restarts and no killing of in-flight runs without asking.**
- The sandbox envelope: role `docker_sandbox_slice` (`fabro-sandbox.slice`, MemoryMax 24G, CPUQuota 1400%), shared by every Docker container on hp.
- Swap and container storage: role `sandbox_storage` (160 GiB swap on sdc1, stores on sdc2).
- Method for setting any cap: `.ai/ci-node-capacity-reads.md`. The cap is throughput-derived (successes per hour), not utilisation-derived. hp's 15-minute-load target of 24 (150% of 16 cores) is a SOFT cap, and going over it is not by itself a reason to step down (maintainer ruling 2026-10-13). The decisive signals are OOM kills, successes per hour and the infrastructure-type failure share.
